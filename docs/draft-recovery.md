# Draft recovery ownership

Recovery belongs to a user and mailbox. A new session for the same user can recover earlier unfinished drafts. Session IDs authorize access and cleanup; they do not partition the saved drafts.

The browser mail database uses schema version 3. Its `recovery` store holds checkpoints with opaque revisions. `recoveryAuthority` has one occupied unique slot keyed by the active session and activation epoch. A checkpoint queues a put of its captured immutable authority row alongside its payload mutation. A stale primary key conflicts with the occupied slot and aborts the entire transaction. Logout leaves a tombstone in that slot, so an old checkpoint cannot become the first writer after cleanup. Recovery revocation is recorded separately from query-cache revocation so either cleanup branch can run even when the other fails.

`AppProviders` observes the authenticated session ID, including changes for the same user. `ComposeSurface` awaits the journal connection, migration, and initial recovery lookup before creating an editor when storage is available. Storage failure reports the existing recovery warning and leaves composition usable. Remote draft and attachment loading failures retain their existing blocking behavior. Each editor and recovery notice uses a capability fixed to its requested session. Resume rereads the latest checkpoint. Discard and completed recovered drafts remove an exact revision, so an older action cannot delete a newer checkpoint with the same timestamp.

The final checkpoint must queue all IndexedDB requests and call `commit()` synchronously on the already-open, authorized connection. Awaiting an authority read before queuing the payload can lose the checkpoint during immediate navigation. Ordinary callers await the returned promise and handle storage failures through the existing error reporting. The pagehide handler starts the same operation without awaiting it.

Each save immediately queues a separate guarded pruning transaction. Awaited saves, startup migration, and reads enforce the recovery limit. Navigation can terminate pruning after the critical checkpoint commits, leaving temporary extra rows for the same owner. The next active read or startup removes those rows. Cleanup clears every raw recovery row, including surplus records, while its captured authority remains current.

Sign-out and deletion capture query-cache and journal cleanup closures before awaiting authentication. Native sign-out captures those closures through its renderer handshake before starting the provider request. A successful action independently attempts both closures. A later activation makes the older cleanup harmless. An anonymous observation without a previous activation grants no cleanup authority. Failed cleanup fences the local editor and reports failure; a storage transaction that cannot commit does not establish durable revocation in other contexts.

Migration validates the user and mailbox in legacy localStorage records, copies eligible records into a guarded IndexedDB transaction, and removes the legacy keys only after that transaction commits. The same transaction durably consumes legacy import. Cleanup also consumes import, including cleanup before the first migration, so leftover localStorage cannot revive logged-out recovery. Repeated migration preserves newer checkpoints already in IndexedDB. Logout also removes legacy keys. Already-loaded older clients continue their previous storage protocol until they reload; the transactional guard protects clients running the new schema.
