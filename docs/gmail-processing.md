# Gmail background processing

Gmail push requests authenticate Google's token and validate the subscription and notification before writing to `GmailProcessingQueue`. A successful response means that the queue accepted the notification. The realtime Worker dispatches fresh mail immediately, independently of older capture and reconciliation work. Queues preserve accepted work across disconnects and retries.

The production Pub/Sub subscription has a 30-second acknowledgment deadline. Pub/Sub closes the push request when that deadline expires. Processing used to run inside that request, although capture alone could take 45 seconds. Cancellation left the mailbox processing lease behind, and retries returned busy until it expired. Queue delivery removes that request lifetime from processing. A longer HTTP timeout or `waitUntil()` alone would still leave work dependent on a terminating request. See [Pub/Sub subscription deadlines](https://docs.cloud.google.com/pubsub/docs/reference/rest/v1/projects.subscriptions) and [Cloudflare invocation limits](https://developers.cloudflare.com/workers/platform/limits/).

Discovery, fresh execution, and catchup have separate queues and consumer capacity. They use batches of one with no batching delay. Discovery probes the newest recent messages and persists work before waking fresh execution. Gmail documents `messages.list` as [newest first](https://developers.google.com/workspace/gmail/api/guides/list-messages). This probe supplements canonical history processing, which still covers older and imported messages and owns the history cursor. The probe never advances that cursor.

Fresh execution has four concurrent consumers. Catchup has two. New work selects the newest ready message and claims it atomically. Different messages can execute in parallel. Duplicate notifications converge on one mailbox/message row, and claim tokens fence completion. The existing mailbox lease protects canonical capture and cursor changes without blocking fresh execution. Message leases outlast the platform's 15-minute consumer lifetime.

Labeling and code detection run concurrently over one complete normalized message fetch. Their fixed-model requests reserve bounded credit capacity instead of the whole account balance. Provider price filters, validated context bounds, and extraction output limits constrain those reservations. Generic AI requests retain exclusive admission. Account and team limits, unresolved holds, and settlement identities remain enforced. Code screening still precedes extraction because its result determines whether extraction is needed.

Critical completion means that enabled labeling and code processing have both succeeded. Capture persistence, memory, actions, and reminder observations run after the critical attempts settle. The capture snapshot comes from the same full provider response and normalization path. Canonical capture skips already retained revisions while preserving the established upgrade from search-only capture. Each feature retains its own retry deadline. The earliest pending deadline wakes message work, and a durable mailbox provider cooldown pauses sibling requests when Gmail throttles them. Temporarily disabled labeling can resume existing pending events when enabled again.

Completed and ignored deliveries acknowledge. Busy and failed attempts retry. Continuations are sent durably before the current delivery acknowledges. Maintenance repairs missing wakeups from durable work rows. Each queue has a dead-letter queue, and pending rows remain available for recovery.

Inspect queue depth, delivery failures, and dead letters alongside the realtime Worker's `gmail_processing_queue_error` reports. Compare `gmailWatchState.lastNotificationAt`, `lastProcessedAt`, `providerRetryAt`, and `lastError` with capture state, message work, and pending labeling or verification events. Cast timestamp columns to text in the PlanetScale web console when comparing them with UTC logs. Its timestamp display can use the browser's time zone. Queue payloads contain private mailbox identifiers and addresses and must stay out of public logs and screenshots.

The Worker emits `gmail_critical_complete` only for successful critical work. Numeric fields include code, labeling, combined execution, work wait, and notification-to-completion durations. Separate outcome records count idle, deferred, and failed attempts. These logs contain no message content or identifiers. Five to ten seconds is an average latency goal, not a deadline for canceling or dropping accepted mail. Report failures and deferred work separately from successful latency samples.

`gmail_processing_attempt` records each claimed work invocation, including exceptions and finish failures. Idle invocations retain their separate outcome record. `messageAttempts` contains one snapshot per authorized message invocation, at most two when authorization refresh retries the operation. `authorizationMs` adds the intervals outside those invocations. Each snapshot freezes `criticalMs`, `autoLabelMs`, and `verificationCodeMs` before the completion callback and follow-up work. `followUpMs` measures capture, memory, and action observations separately.

Label stages record inclusive elapsed milliseconds and visited-call counts. An absent stage did not run. `returned` means that the function returned, including any internal fallback. It does not prove that history loaded or usage reporting succeeded. Classifier time includes credit admission, provider work, and settlement. The label path separates new classification, recovered classification, already-applied events, and other no-ops. Select fresh, previously unfinished work with a completed `new_classification` path and saved application for a fresh decision cohort. Zero selected labels still count as a decision.

`queueMs` retains its original work-creation-to-account-lookup definition and includes earlier retries. `workAgeMs` ends at claim completion. `dueLatenessMs` measures lateness against the claimed due date. `notificationAgeMs` ends at handler entry. None is pure queue transport latency. `gmail_fresh_discovery_attempt` separates discovery and wake scheduling, with notification age, listed-message count, and attempted wake calls. Listed messages are not newly inserted work. Compare stages within each attempt, and keep retries, errors, and no-ops separate. These identifier-free logs cannot establish unique-mail counts or guarantee a final record after process termination. Use durable event transitions for unique-mail latency samples.

SST owns the queues and consumers. Producer queues exist before their bindings deploy, so accepted notifications remain durable during consumer installation. Production rollout requires explicit authorization and the protected deployment workflow. Apply the additive migrations before deploying code that reads the new work and cooldown fields. Preserve accepted queue contents.

Drain legacy automation invocations before enabling the new consumers. The rollout marker detects an active legacy mailbox lease, but an unmodified old worker cannot honor new message claims. Pause old processing behind durable intake during that handoff. Do not roll back to an unclaimed legacy processor while new message work is running. The web restore button does not restore background bindings. Use a reviewed forward fix or a controlled processing handoff. Authorized recovery can redeliver dead letters after fixing their cause.

## Local verification

Run `vp run env:doctor`, then `vp run dev:workers` on an unused port. The local Worker uses Wrangler's persistent queue simulation and the same queue handler as production. `/__dev/pubsub` retains its local bearer authentication and subscription check, then acknowledges durable enqueueing. `vp run dev:pubsub` pulls only the separate development subscription and acknowledges Google after that local handoff.

Check acceptance and completion separately. The HTTP response should arrive before message processing finishes. Disconnecting the caller after acceptance must not stop queued work. Inject a distinct fresh message while older work is already running. Verify the saved label classification and decrypt the saved code, rather than timing discovery alone. Duplicate notifications should converge without another provider label change or a duplicate usage charge. Keep shared Gmail in observation mode with production watch ownership. Stop the task's local process tree after verification. See [development setup](development.md) for credentials and mailbox isolation, and [Cloudflare's local queue development](https://developers.cloudflare.com/queues/configuration/local-development/) for the simulator's limits.
