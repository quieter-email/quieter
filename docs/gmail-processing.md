# Gmail background processing

Gmail push requests authenticate Google's token and validate the subscription and notification before writing to `GmailProcessingQueue`. A successful response means that the queue accepted the notification. Mail capture, labeling, code extraction, and other message work run in the queue handler on the existing Gmail realtime Worker. They use the established mailbox authorization, event records, billing, and history cursors.

The production Pub/Sub subscription has a 30-second acknowledgment deadline. Pub/Sub closes the push request when that deadline expires. Processing used to run inside that request, although capture alone could take 45 seconds. Cancellation left the mailbox processing lease behind, and retries returned busy until it expired. Queue delivery removes that request lifetime from processing. A longer HTTP timeout or `waitUntil()` alone would still leave work dependent on a terminating request. See [Pub/Sub subscription deadlines](https://docs.cloud.google.com/pubsub/docs/reference/rest/v1/projects.subscriptions) and [Cloudflare invocation limits](https://developers.cloudflare.com/workers/platform/limits/).

The queue consumer processes one notification per batch and uses the existing mailbox lease to serialize changes. Its lease outlasts the platform's 15-minute consumer lifetime. Completed and ignored notifications acknowledge. Busy and failed attempts retry. Successful work with more pages durably enqueues its continuation before acknowledging the current notification. A disconnect after enqueueing can produce duplicate notifications; the existing message records and stable usage identities remain responsible for convergence.

`GmailProcessingDeadLetterQueue` retains notifications that exhaust the retry limit. Inspect queue backlog, delivery failures, and dead letters alongside the realtime Worker's `gmail_processing_queue_error` reports. Compare the affected mailbox's `gmailWatchState.lastNotificationAt`, `lastProcessedAt`, `processingLeaseExpiresAt`, and `lastError` with its capture state and pending labeling or verification records. Cast timestamp columns to text in the PlanetScale web console when comparing them with UTC logs; the console can render timestamp-without-time-zone values using the browser's time zone. Queue messages contain mailbox addresses and must stay out of public logs and screenshots.

SST owns both queues and the consumer. It creates the producer queue before deploying its binding, so notifications accepted during consumer installation remain queued. Use the protected production deployment workflow for rollout. This changes background bindings, so the web restore button does not restore the processing system. Use a reviewed forward fix and preserve the consumer and accepted queue contents until they drain. Authorized recovery can redeliver dead letters after fixing their cause.

## Local verification

Run `vp run env:doctor`, then `vp run dev:workers` on an unused port. The local Worker uses Wrangler's persistent queue simulation and the same queue handler as production. `/__dev/pubsub` retains its local bearer authentication and subscription check, then acknowledges durable enqueueing. `vp run dev:pubsub` pulls only the separate development subscription and acknowledges Google after that local handoff.

Check acceptance and completion separately. The HTTP response should arrive before message processing finishes. Disconnecting the caller after acceptance must not stop queued work. Inspect development processing cursors and label and code records afterward. Duplicate notifications should converge without another provider label change or a duplicate usage charge. Keep shared Gmail in observation mode with production watch ownership. Stop the task's local process tree after verification. See [development setup](development.md) for credentials and mailbox isolation, and [Cloudflare's local queue development](https://developers.cloudflare.com/queues/configuration/local-development/) for the simulator's limits.
