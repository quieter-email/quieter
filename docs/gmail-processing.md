# Gmail background processing

Gmail Pub/Sub push enters `GmailRealtimeWorker`, which validates the Google JWT and subscription before forwarding the notification to the private processor. The processor resolves the connected mailbox and commits its wake to the mailbox's Durable Object before returning success. The gateway can then acknowledge Pub/Sub and notify the mailbox's live clients while processing continues. Push history IDs are observations. The Durable Object uses them to coalesce duplicate notifications, and the history readers keep their own checkpoints.

## Scheduling

One SQLite-backed `GmailMailboxScheduler` owns the schedule for each immutable mailbox ID. The schedule has separate lanes for discovery, fresh message work, history sync, and catch-up work. A wake updates the pending deadline even when the same lane is running. The alarm commits a dispatch token and a recovery deadline before sending a job. The first delivery to claim the token can run the task. A delayed delivery can still claim a token that has been resent, and a completion from an expired execution cannot advance the schedule.

Four fresh queue shards carry discovery, live history sync, and fresh message work. Four catch-up queue shards carry reconciliation and recovery. Four automation shards carry Actions, importance, memory and semantic indexing, and reminder evaluations. Mailbox IDs select queue shards. Jobs carry the mailbox ID, task, dispatch token, and the Gmail revision and receipt timestamp when the job came from a notification. Fresh batches process up to two messages, catch-up batches process up to six, and each mailbox runs one Action at a time. Inbox Actions enter their lane after message work persists. Manual Actions and Gmail connection changes send a signed wake after the database commit. Indexed repair can restore a missed wake.

The history executor uses one all-change stream. It stages additions and a durable capture manifest in the same leased Postgres transaction before moving the checkpoint. It applies captured label changes and deletes from the manifest. During rollout it replays from the older legacy position and preserves both compatible checkpoints. At the head of the stream, a notification runs history without a recent-message list probe. Bootstrap and recovery retain the independent recent-first discovery route. A complete live history page sends its added-message work to the fresh lane while keeping the recovery eligibility checks for imported or old mail.

Newly discovered catch-up messages get automatic labeling only when eligible unread inbox mail is within 48 hours, code detection within two hours, and Actions and reminder observations within 24 hours. Existing label and code events can finish through their existing retry paths. A message batch reuses label context and reads memory only when a paid classification can use it. The model calls still require plan entitlements and existing credit reservations.

Successful sync schedules the next reconciliation and checks watch renewal. The indexed repair cron reserves due mailbox rows, then asks the actor to sync. It reissues automation wakes and enrolls legacy mailboxes once in keyset order. Each mailbox prunes its own terminal message work after 30 days during periodic sync. Unfinished effects remain recoverable. An actor retires only after its sync executor observes that the mailbox row has been deleted. Reauthentication for the same mailbox keeps its pending work and resets the repair deadline.

## Provider capacity

`QUIETER_GMAIL_BACKGROUND_QUOTA_UNITS_PER_MINUTE` is the allocation for Gmail background work in this deployment. Set it from the actual API allocation after reserving room for interactive Gmail calls and other clients of the project. The default is 600,000 background units per minute. Sharded quota objects meter method costs at the request boundary, including retries and each part in a batch. Watch renewal and live processing have reserved budgets and can borrow unused catch-up units. Gmail's explicit project-wide daily exhaustion pauses all background lanes. Per-user or ambiguous throttling stays in the individual mailbox's cooldown.

`QUIETER_GMAIL_BACKGROUND_AI_REQUESTS_PER_MINUTE` optionally bounds deferrable model starts. An explicit provider rate limit also pauses deferrable classification, importance, and memory work. Model admission happens before the billing reservation. Fresh code and label requests retain priority and their existing credit checks. Running Actions and reminders keep their effect and billing guards.

Record the production project allocation and measure average and peak method cost before expanding the cohort. Gmail enforces external quotas and Cloudflare enforces per-queue dispatch limits. [Gmail quota](https://developers.google.com/workspace/gmail/api/reference/quota) · [Cloudflare queue limits](https://developers.cloudflare.com/queues/platform/limits/)

## Release and recovery

Apply the nullable repair column migration before changing workers. The second migration builds the repair and work indexes concurrently. Check the indexes are valid and the queue and consumer bindings exist before moving traffic. The processor stays private and retains the existing Hyperdrive and Secret bindings. The configured Worker placement and the first-use location of a Durable Object are separate. Compare receipt latency, queue age, and database timings after deploying.

Keep the legacy queues and the `GmailFreshExecutor` migration while pending items drain. Existing queue deliveries and legacy alarm demand are translated into mailbox wakes. Quieter can recover pending message rows by replaying a sync wake for a mailbox. If a delivery or completion fails, inspect the dispatch lane, queue age, dead letters, and the mailbox's provider cooldown. An unresolved provider response can still retain a billing hold. A schedule token fences the schedule, and a message claim fences the work-row update. Neither controls a request already accepted by an external provider.

For recovery, use a forward deployment that keeps both Durable Object namespaces and finishes outstanding dispatches. Returning to a version that cannot read the new schedule requires stopping new dispatches, retaining accepted intake, waiting for in-flight provider work to drain, and replaying the pending lanes into an active processor. Drain the automation lane state before restoring an older class that cannot dispatch it, since those due lanes could otherwise cause repeated alarms. Keep both Postgres checkpoints and unfinished work during that handoff.

Track oldest ready work by lane, queue retries, watch expiry margin, provider throttling, and unresolved billing outcomes during a rollout. Validate the limits of the configured Gmail project, model budget, and database before expanding. Keep both legacy-compatible history columns through the rollback window. Confirm that old executors and queue messages have drained before removing any legacy resources.

## Local verification

Run `vp run env:doctor`, then `vp run dev:workers`. The gateway listens on loopback and calls the auxiliary private processor through a native Worker service binding. Both use the ignored bindings prepared by `dev:prepare`. To choose another port, update the local URLs, run `vp run dev:prepare`, then run `vp run @quieter/cloudflare#dev --port <port>`. See [development setup](development.md) and [Cloudflare's local queue documentation](https://developers.cloudflare.com/queues/configuration/local-development/).

Use the local bearer-protected `/__dev/pubsub` to check notification acceptance and `/__dev/maintenance` to exercise repair. For real Gmail mutations, use a dedicated development mailbox with separate watch and Pub/Sub ownership. Send a new message while catch-up is running. Observe both the queue delivery and the saved output. Redeliver the same notification and verify it converges to one work record and one billing outcome. Keep shared Gmail in observe mode with production watch ownership. Stop the owned process tree after verification.
