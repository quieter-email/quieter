# Gmail background processing

Gmail push requests authenticate Google's token and validate the subscription and notification before writing to `GmailProcessingQueue`. A successful response means that the queue accepted the notification. Fresh mail has a separate execution route from older capture and reconciliation work. Queues preserve accepted work across disconnects and retries.

Native queue delivery remains in `GmailRealtimeWorker`. It forwards each complete notification, capture, or work job through the private `GmailProcessingWorker` service binding. Fresh work acknowledges after a `GmailFreshExecutor` accepts its durable wake. Notifications, capture, and catchup run the established processing path in the private fetch handler. The queue handler validates the returned acknowledgment or delayed retry decision. Transport errors, non-success responses, and invalid decisions retry after 60 seconds.

SST configures the processor with `placement: { region: "aws:eu-central-1" }`, the existing Hyperdrive database, processing Secret links, billing and release settings, queue producers, and the cross-script `MailLiveUser` binding. Durable Object migrations remain with their original owners. The processor has no public route, workers.dev URL, or version preview URL. The realtime Worker depends on the processor component and its private URL resource, including the component's placement child. The protected release verifier checks its build, placement, URL settings, and caller binding alongside every existing Action producer.

[Placement applies to the default fetch handler](https://developers.cloudflare.com/workers/configuration/placement/). It does not place Durable Object alarms. Only validated private fetch calls resolve the four fixed executor names, using EU jurisdiction and a best-effort western Europe hint. [Object location depends on the first caller](https://developers.cloudflare.com/durable-objects/reference/data-location/), without a Frankfurt guarantee. Measure actual database stages and receipt latency before accepting a placement change. Retain slow samples, retries, and failures in the receipt cohort and report their outcomes.

The production Pub/Sub subscription has a 30-second acknowledgment deadline. Pub/Sub closes the push request when that deadline expires. Processing used to run inside that request, although capture alone could take 45 seconds. Cancellation left the mailbox processing lease behind, and retries returned busy until it expired. Queue delivery removes that request lifetime from processing. A longer HTTP timeout or `waitUntil()` alone would still leave work dependent on a terminating request. See [Pub/Sub subscription deadlines](https://docs.cloud.google.com/pubsub/docs/reference/rest/v1/projects.subscriptions) and [Cloudflare invocation limits](https://developers.cloudflare.com/workers/platform/limits/).

Discovery, fresh execution, and catchup have separate queues and consumer capacity. They use batches of one with no batching delay. Discovery probes the newest recent messages and persists work before waking fresh execution. Gmail documents `messages.list` as [newest first](https://developers.google.com/workspace/gmail/api/guides/list-messages). This probe supplements canonical history processing, which still covers older and imported messages and owns the history cursor. The probe never advances that cursor.

Four fixed `GmailFreshExecutor` objects execute fresh work in parallel. Each alarm awaits one complete `processGmailJob` turn directly, including follow-ups. The alarm creates no HTTP processing child. Catchup retains two native consumers. New work selects the newest ready message and claims it atomically. Fresh admission serializes its active-lease count and claim, deferring a new claim when four fresh leases are already active. Unfinished follow-ups occupy capacity. Promotion from independently bounded catchup can conservatively increase that count. Duplicate notifications converge on one mailbox/message row, and claim tokens fence completion. The existing mailbox lease protects canonical capture and cursor changes without blocking fresh execution.

After discovery and canonical capture persist their work, scheduling reads unfinished work for each mailbox and priority. Completed rows produce no work wakes. Ready work retains bounded parallel fan-out. Future due dates, active leases, and provider cooldowns leave one durable delayed wake. Unfinished Actions still require scheduling after critical completion. Read or send failures retry the canonical job, and raw discovery always publishes capture even when no fresh work remains. Claims, work-branch wake scheduling, and maintenance remain the recovery authority when this readiness snapshot races another worker.

Fresh scheduling accepts the native queue fallback before it pokes the alarm owners. One ready batch wakes at most four distinct owners. A native delivery wakes one stable owner. An alarm schedules its continuation locally. Indexed mailbox deadlines, service order, and generations preserve demand that arrives during processing. A persisted recovery alarm precedes the processing call. The platform's 15-minute alarm lifetime ends before the 16-minute work lease can expire. Native delivery and maintenance can restore missing wakes. Remote provider uncertainty retains its existing billing hold.

Labeling and code detection run concurrently over one complete normalized message fetch. Their fixed-model requests reserve bounded credit capacity instead of the whole account balance. Provider price filters, validated context bounds, and extraction output limits constrain those reservations. Generic AI requests retain exclusive admission. Account and team limits, unresolved holds, and settlement identities remain enforced. Code screening still precedes extraction because its result determines whether extraction is needed.

Critical completion means that enabled labeling and code processing have both succeeded. Capture persistence, memory, actions, and reminder observations run after the critical attempts settle. The capture snapshot comes from the same full provider response and normalization path. Canonical capture skips already retained revisions while preserving the established upgrade from search-only capture. Each feature retains its own retry deadline. The earliest pending deadline wakes message work, and a durable mailbox provider cooldown pauses sibling requests when Gmail throttles them. Temporarily disabled labeling can resume existing pending events when enabled again.

Completed and ignored deliveries acknowledge. Busy and failed attempts retry. Continuations are sent durably before the current delivery acknowledges. Maintenance repairs missing wakeups from durable work rows. Each queue has a dead-letter queue, and pending rows remain available for recovery.

The alarm awaits processing, broadcasts, and wake scheduling before returning. It does not detach business work with `waitUntil()`. A lost acceptance response can redeliver a wake, and interruption can leave the existing work lease active until expiry. Generation checks, token-checked claims, and durable checkpoints retain recovery ownership.

Inspect queue depth, delivery failures, and dead letters alongside the processor's `gmail_processing_queue_error` and realtime Worker's `gmail_processing_transport_error` reports. Compare `gmailWatchState.lastNotificationAt`, `lastProcessedAt`, `providerRetryAt`, and `lastError` with capture state, message work, and pending labeling or verification events. Cast timestamp columns to text in the PlanetScale web console when comparing them with UTC logs. Its timestamp display can use the browser's time zone. Queue payloads contain private mailbox identifiers and addresses and must stay out of public logs and screenshots.

The Worker emits `gmail_critical_complete` only for successful critical work. Numeric fields include code, labeling, combined execution, work wait, and notification-to-completion durations. Separate outcome records count idle, deferred, and failed attempts. These logs contain no message content or identifiers. Five to ten seconds is an average latency goal, not a deadline for canceling or dropping accepted mail. Report failures and deferred work separately from successful latency samples.

`gmail_fresh_alarm_complete` records the alarm outcome, total processing time, and lateness against its selected wake deadline. That lateness includes owner scheduling and fairness, so it is not pure transport latency. The private fetch placement header describes acceptance rather than alarm execution. Use Gmail receipt time and the later durable label or code completion for the end-to-end metric.

`gmail_processing_attempt` records each claimed work invocation, including exceptions and finish failures. Idle invocations retain their separate outcome record. `messageAttempts` contains one snapshot per authorized message invocation, at most two when authorization refresh retries the operation. `authorizationMs` adds the intervals outside those invocations. Each snapshot freezes `criticalMs`, `autoLabelMs`, and `verificationCodeMs` before the completion callback and follow-up work. `followUpMs` measures capture, memory, and action observations separately.

Label stages record inclusive elapsed milliseconds and visited-call counts. An absent stage did not run. `returned` means that the function returned, including any internal fallback. It does not prove that history loaded or usage reporting succeeded. Classifier time includes credit admission, provider work, and settlement. The label path separates new classification, recovered classification, already-applied events, and other no-ops. Select fresh, previously unfinished work with a completed `new_classification` path and saved application for a fresh decision cohort. Zero selected labels still count as a decision.

`queueMs` retains its original work-creation-to-account-lookup definition and includes earlier retries. `workAgeMs` ends at claim completion. `dueLatenessMs` measures lateness against the claimed due date. `notificationAgeMs` ends at handler entry. None is pure queue transport latency. `gmail_fresh_discovery_attempt` separates discovery and wake scheduling, with notification age, listed-message count, and attempted wake calls. Listed messages are not newly inserted work. Compare stages within each attempt, and keep retries, errors, and no-ops separate. These identifier-free logs cannot establish unique-mail counts or guarantee a final record after process termination. Use durable event transitions for unique-mail latency samples.

SST owns the queues and consumers. Producer queues exist before their bindings deploy, so accepted notifications remain durable during consumer installation. Production rollout requires explicit authorization and the protected deployment workflow. Apply the additive migrations before deploying code that reads the new work and cooldown fields. Preserve accepted queue contents.

Drain legacy automation invocations before enabling the new consumers. The rollout marker detects an active legacy mailbox lease, but an unmodified old worker cannot honor new message claims. Pause old processing behind durable intake during that handoff. Do not roll back to an unclaimed legacy processor while new message work is running. The web restore button does not restore background bindings. Use a reviewed forward fix or a controlled processing handoff. Authorized recovery can redeliver dead letters after fixing their cause.

Before enabling direct alarm execution, positively verify completion of old fresh HTTP attempts and their leased work. Elapsed time alone does not establish that an old HTTP child stopped. Preserve the executor class, namespace migration, claim gate, and pending schedules during a forward fix or drain. Do not restore the old fresh HTTP execution route while alarm demand remains.

## Local verification

Run `vp run env:doctor`, then `vp run dev:workers` on an unused port. Wrangler loads `wrangler.local.jsonc` and `wrangler.processing.local.jsonc` in one [native multi-Worker session](https://developers.cloudflare.com/workers/local-development/multi-workers/). Only the gateway listens on loopback port 8787. The processor is auxiliary and reachable through its service binding. Both read the ignored `.dev.vars` prepared from approved development settings. The gateway owns its existing consumers and Durable Objects. The processor owns the SQLite-backed `GmailFreshExecutor` namespace and its `fresh-v1` migration, queue producers, and cross-worker broadcast binding. Native local execution uses an unrestricted namespace because workerd does not implement jurisdiction restrictions. It does not prove production placement.

The local graph uses persistent queue simulation and the production queue adapter and processor. `/__dev/pubsub` retains its local bearer authentication and subscription check, then acknowledges durable enqueueing. `vp run dev:pubsub` pulls only the separate development subscription and acknowledges Google after that local handoff. To use another available port, update the loopback `MAIL_UPDATES_URL` and `GMAIL_LIVE_SYNC_URL` in the ignored local settings, run `env:doctor`, then run `vp run dev:prepare` followed by `vp run @quieter/cloudflare#dev --port <port>`. The bridge, fixtures, and manual triggers use the gateway origin from `MAIL_UPDATES_URL`. Record the owned process PID before verification.

Check acceptance and completion separately. The HTTP response should arrive before message processing finishes. Disconnecting the caller after acceptance must not stop queued work. Inject a distinct fresh message while older work is already running. Verify the saved label classification and decrypt the saved code, rather than timing discovery alone. Duplicate notifications should converge without another provider label change or a duplicate usage charge. Keep shared Gmail in observation mode with production watch ownership. Stop the task's local process tree after verification. See [development setup](development.md) for credentials and mailbox isolation, and [Cloudflare's local queue development](https://developers.cloudflare.com/queues/configuration/local-development/) for the simulator's limits.
