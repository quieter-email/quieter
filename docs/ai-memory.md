# AI memory

quieter stores categorized plain-text facts about each user. The system learns from mail content, authored writing, conversations and meaningful actions. It consolidates new evidence into existing concepts. Hybrid recall combines existing SQL selection with versioned embeddings stored in PostgreSQL. The same embedding adapter supports conversation and retained-mail search; no external vector database is required.

## Ownership and authority

Every fact belongs to one user. Their general preferences and writing style follow them across their mailboxes. A label rule can carry a source mailbox ID because label IDs and label policies apply within a particular mailbox. This limits where the rule applies without changing its owner.

A mailbox grant never grants access to another user's memories. Explicit interactions with a shared mailbox can inform the acting user's profile. Unattended shared-mailbox work has no personal-memory owner and uses operational mail history only. Private-mailbox automation can load its verified owner's preferences. The billing identity never supplies personal context. Legacy ownerless mailbox facts are ignored rather than assigned to someone.

Only the acting user's explicit statements can establish instructions. Sent mail is evidence of writing style and durable facts. Received mail, quoted text, forwarded correspondence and connector results are untrusted evidence. They cannot change permissions, create instructions or overwrite explicit preferences. Secrets, verification codes and financial identifiers are excluded from long-term memory.

## Facts and consolidation

Facts have a concise text body, category, concept key, source, confidence, importance, confirmation date, reinforcement count, optional expiry and optimistic version. Exact correspondent addresses distinguish a person's specific voice from general writing habits. The categories are identity, writing style, relationships, preferences, work, interests, activity and labeling.

The writer sees actual authored text, sentence structure, wording, greetings and sign-offs. Brief examples are allowed when they explain the user's voice. Quoted replies are stripped from authored samples. Draft evidence remains provisional. Generated replies, chat compose output and formatted dictation leave only scoped text fingerprints. Capture recognizes unchanged generated text, including automatic mailbox signatures, and excludes it from voice evidence. Repeated external sent samples remain cautious evidence rather than proof of human authorship. Substantive edits and output generated by another application cannot be attributed perfectly.

Consolidation recalls general facts from each relevant category and searches the user's entire profile for text and contact matches before applying a bounded writer input. It updates an existing concept when evidence changes, rather than appending an exhaustive mail summary. Admission keeps concepts that can help a future decision about the user. Routine receipts, service alerts, temporary balances, shipment timelines, marketing, and one-off incident summaries normally add nothing. Independently supported lasting context can still be extracted from them. Malformed or past intended expiries discard the proposed mutation instead of making it permanent. Records without intended expiry remain eligible.

Normal learning conservatively reviews obsolete or noisy nonexplicit learned records it actually recalls. This is gradual historical curation, with no total record cap or separate cleanup job. Recent evidence receives more weight. Explicit facts and instructions are retained unless corrected, forgotten or given an expiry. Old, unconfirmed, low-confidence inferred facts can stop contributing to context.

## Capture

| Source | Learning |
| --- | --- |
| Onboarding and mailbox connection | Queue separate samples of up to 50 recent received and 50 sent messages. |
| Incoming Gmail and messages sent from another client | Capture through Gmail history and recovery independently of auto-label settings. |
| Managed incoming mail | Capture during durable ingestion, including retried deliveries. |
| Thread opens and AI mail reads | Reuse fetched content, including messages already marked read. |
| Compose drafts and successful sends | Capture authored revisions and final accepted text. |
| Bulk mail actions | Persist message IDs first, then hydrate message evidence in the memory worker. |
| Label corrections | Rebuild deterministic label policies from owned manual correction evidence. |
| Importance feedback | Learn handling preferences with the action and sender evidence. |
| User chat | Queue ordinary messages. Apply explicit additions, corrections and forgetting before the answer. |

Source keys deduplicate provider deliveries, refetches and retries. Reading the same message repeatedly does not make its claims stronger. Bootstrap state keeps separate cursors, counts and completion flags for received and sent samples. It is checkpointed and retried through scheduled mail maintenance. The account learning status and retry API expose incomplete scans without adding separate memory owners. A change of private mailbox owner starts a fresh scan for that owner and cancels the previous scan's lease.

## Initial context and further recall

Every contextual generation uses `loadAiAgentContext` from the public `@quieter/orpc/ai-memory` module. Its implementation in `ai-memory-context.ts` selects owned records with SQL and rechecks access whenever a mailbox is supplied. Every call selects only the acting user's facts. Mailbox-specific label rules enter generation only when the source mailbox matches. Cached candidate handles contain identities, never a previously authorized copy of private facts, and cannot be reused by another actor.

The loader reserves space across task-specific categories, includes applicable instructions and exact correspondent knowledge, then fills remaining space by relevance and salience. SQL matches the stored collection before applying per-category, contact and lexical result limits. Contextual generation can opt into billable query embeddings and bounded preparation of missing source chunks. Vector candidates join the existing selection; they do not replace instruction, category, contact or keyword retrieval. Final ranking accepts semantic matches only for the current fact version. Original query contacts still determine correspondent applicability. Similarity cannot create instruction authority or mailbox access.

The shared adapter uses multilingual `baai/bge-m3` dense embeddings at 1024 dimensions through the existing linked OpenRouter credential. Its stored identity is `baai/bge-m3:1024:v1`. Source chunks and queries use the same fixed model. The adapter requires private routing, validates model identity, result correspondence and finite nonzero vectors, and uses the existing credit reservation ledger. Access is checked before and after inference. Known costs settle even if later vector validation fails. An uncertain paid request fails the operation and keeps its reservation. Known-cost holds use normal reconciliation. Unknown outcomes without a usable provider generation ID require the existing [single-reservation recovery procedure](billing.md#recover-one-interrupted-ai-reservation); they are not automatically released. The former model-generated query-expansion path is removed. The loader still owns the prompt budget, so consumers must not truncate selected context again.

The provider boundary accepts the requested identity and the observed `BAAI/bge-m3` and `parasail-bge-m3` response aliases. Other models remain invalid even when their dimensions match. BGE-M3 supplies one dense vector per chunk; its sparse and multivector modes are not used. Native TIN text retrieval remains the independent lexical lane.

Chat, reply suggestions, dictated-mail formatting, mail importance, auto-labeling and natural-language mail search receive task-specific context before generation. Strict verification-code extraction, transcription and administrative generation remain evidence-only. Chat can search or page through further memories with `read_personal_context`. Live calendar questions use connected calendar reads and current event evidence, never remembered availability.

Auto-labeling also receives transient algorithmic history from the same mailbox. Exact sender examples and weaker same-domain examples are separate, bounded lanes. The target message, outbound mail, drafts, spam and trash are excluded. Address parsing uses the actual mailbox address, including quoted display names and folded headers; lookalike domains do not qualify.

Each example separates current labels, confirmed prior automatic applications and known user additions or removals. Gmail labels are read live; managed-mail labels include their recorded assignment source. Both use the current label dictionary, including labels whose automatic matching is disabled. A changed Gmail label alone is not claimed to be a manual correction. A planned but unapplied classification is not historical application evidence. Current explicit instructions and the new message's purpose remain decisive; prior automatic labels cannot establish a user preference by themselves.

History reads and personal-context reads run together only when a model decision is needed and the normal budget check has passed. History does not call another model or require the classifier to invoke tools. Optional history read failures report sanitized diagnostics and leave preference-based classification available; revoked access still aborts the operation.

## Extending another feature

Server-side features use the same read entry point, whether or not they involve mail. Take `userId` from the authenticated service context or a background job's verified ownership decision. These internal functions do not authenticate an arbitrary user ID: never take it from a request body, remembered text or model output. Worker callers use the normal request-specific database client boundary.

Existing consumers keep their defaults. A future task can supply a typed selection without changing storage or adding another recall path:

```ts
import {
  loadAiAgentContext,
  serializeAiAgentContext,
} from "@quieter/orpc/ai-memory";
import type { AiMemoryContextSelection } from "@quieter/orpc/ai-memory";

const selection = {
  categories: ["preferences", "work", "relationships", "activity"],
  characterBudget: 12_000,
} satisfies AiMemoryContextSelection;

const memoryContext = await loadAiAgentContext({
  agent: "calendar_planning",
  query: userRequest,
  selection,
  userId: context.userId,
});
const promptContext = serializeAiAgentContext(memoryContext);
```

Omitting `mailboxId` still loads the user's general memories. A mailbox task supplies its ID to include that mailbox's applicable label rules, with a fresh mailbox access check. `loadAiAgentContext({ overview: { query }, userId })` searches and pages through the user's full profile, including facts with mailbox provenance.

Categories guide balanced SQL retrieval, ranking and space reservations. They are priorities: applicable instructions and relevant lexical or exact correspondent matches may bring in other categories. Agent and correspondent restrictions still apply. Selection requires nonempty known categories, deduplicates them, rejects non-finite budgets and clamps integer budgets to 256 to 32,000 characters. The budget bounds combined `instructions` and `memory` text, including omission notices; the serializer adds fixed framing. Do not truncate the selected context again. Reads do not update facts. Omitting `semantic` keeps task recall model-free. Generation callers pass `semantic: { billingMailboxId, signal }` with a real accessible billing mailbox; its billing identity never selects whose personal facts are read. Calendar context can omit mailbox-specific applicability while retaining the authorized chat mailbox for billing. A nonempty opted-in query can incur embedding usage when eligible sources exist. Empty eligible collections make no provider call. Full-profile browsing and lazy overview pagination remain deterministic and model-free.

For explicit user-authored additions and edits, use `saveAiMemory` with category, content and the authenticated actor's ID. It needs neither a mailbox nor a model call. Edits supply the memory ID and current version; `forgetAiMemory` permanently deletes a fact. There is no scope selector or mailbox-owned memory API. These canonical APIs preserve validation, secret rejection, revision fencing and deletion behavior. Natural-language `requestAiMemoryUpdate` additionally needs a mailbox for model authorization and billing.

Existing mail/chat capture workflows feed `recordAiMemoryEvent` and the canonical consolidation writer using stable deduplication keys. This is an extension seam, not an arbitrary-observation API: event kinds and their SQL constraint are mail/chat-specific, source authority depends on the outer kind, and events require mailbox-backed access and billing. `metadata.observationKind` only refines that evidence. A future calendar/task capture needs a genuine evidence/authorization adapter, a neutral event kind and validated payload, and a personal billing route that does not invent a mailbox, with the corresponding additive migration and worker support. Do not disguise new evidence as chat or mail or weaken migration policy. No such schema change is part of this read extension.

Keep transient algorithmic evidence in its feature's own context, such as recent label-history statistics or live calendar results. Consolidate only durable user facts and preferences into shared memory.

## User control and deletion

Settings shows a searchable list with category filters and counts. Users can add, edit, and delete individual facts. A single options menu controls automatic learning and deleting all memories. `searchAiMemory` returns the authenticated user's active facts and stable pages. Categories guide retrieval and provide filters in Settings. Mailbox provenance and another person's mailbox access do not create separate memory lists.

Manual additions and edits require neither an AI call nor available AI balance. They work while automatic learning is paused. Explicit chat additions and edits also work while paused, with the normal model budget.

Settings and further personal-context reads include the fact's source class, creation date, last confirmation date, optional expiry, internal confidence estimate, and historical reinforcement count. Settings shows the source class and last-supported date, with creation and expiry in the editor. Confidence is uncalibrated and is not displayed as a probability of truth. Reinforcement describes the concept's history rather than a count of independent source messages. These fields do not identify an original email or prove current state. Manual saves clear the previous source reference so user-edited text is not attributed to older evidence. No extra event payloads, message identifiers, or history are retained for this display.

Deleting a fact removes its content and recoverable change snapshots. Reset removes the user's facts, history and label correction evidence, and stops their bootstrap work. Both fence in-flight plans and cancel pending older evidence across the user's mailboxes. Deleting a grouped label rule erases every member source's correction evidence for only the matching actor and source mailbox. Deletion also erases archived deterministic projections and their recoverable history when they share the same mailbox, label and source, including legacy singletons, without removing unrelated correction evidence. Other people's operational corrections remain intact. Scrubbed event-ID tombstones remain to prevent the same provider message from recreating a deleted fact. Reset does not automatically restart onboarding scans. New evidence can establish a fact again; deletion is not permanent suppression of a topic.

The worker claims evidence with a lease, rechecks the user profile revision, learning settings, access, event ownership and touched record versions, then commits facts and event completion together. A late worker cannot clear a newer claim. Processed or canceled payloads are scrubbed. Model failures leave no partial fact changes and retry without duplicating successful events.

Maintenance discovers eligible users and gives each a turn before requeuing more work for the same user. Four workers select fresh evidence for serial user turns, with four consolidation attempts per user and a shared one-minute admission deadline. Already-started work finishes normally. One user's failure or unavailable balance does not stop others. This removes the global four-event selection limit; it does not guarantee fairness across runs during sustained overload. Discovery reads the eligible backlog rather than aggregating all processed history.

The planner sees a bounded set of existing facts, including concept keys and topic matches. General category context precedes mail text matches. If a proposed addition collides with an unseen owned concept, the transaction rolls back and replans with the complete colliding records. At most two recall retries run. An identical concurrently discovered fact completes without a duplicate or another model call. Reviewed targets still require matching versions, and profile revisions still fence explicit changes and forgetting. Automatic plans cannot change another mailbox's specific facts.

Label correction projections group sorted exact sources by label and policy. Global rules, domains, and exact addresses use separate groups so correspondent matching preserves their applicability. Whole-source chunks fit the content and correspondent limits. Typed member metadata preserves every source for deletion. Refresh archives obsolete automatic projections, including historical singletons and old model-generated label summaries for the same mailbox, and leaves explicit edits intact. Evidence represented by an explicit edit is excluded from new automatic groups. Repeated unchanged refreshes leave versions untouched. Label feedback no longer queues model learning; pending legacy label feedback is skipped without billing or model admission. Existing ordinary learned records are curated only when normal learning recalls them.

Chat prefetch reads retained thread headers to select correspondent context. A partial live-thread index matches the mailbox and thread identity. SQL selects recent messages before returning headers; guarded message dates and valid Date-header fallback determine recency. It does not fetch provider content, record an open or run mail automation. A passive selected thread informs retrieval; only explicit attachments enter the attached-context prompt. Genuine user opens and agent thread reads still record their evidence.

## Shared semantic history search

The conversation history menu opens **Search conversations and mail**. Search requires explicit submission rather than calling a model per keystroke. The default dialog shows the query and results; **Search coverage** reveals optional preparation controls. `search.history` checks the acting user and selected mailbox. Chat results contain only that user's user/assistant prose, even in a shared mailbox. Tool payloads and system messages are excluded. Mail results contain current retained messages outside drafts, spam and trash. A result opens the canonical conversation or thread reader; it is not a partial replacement for the rich mail-list contract.

History search combines TIN BM25, a PostgreSQL full-text lane and exact pgvector similarity within the authorized source set. The full-text lane keeps retained content searchable while chunks are still being prepared. Reciprocal rank fusion combines the independently ranked results. Production uses [PlanetScale TIN and pgvector](https://planetscale.com/docs/postgres/search). `vectorscale` is available on the inspected development cluster but is not enabled or used here. No approximate-index performance claim is made.

`semanticEmbedding` stores source-bound chunks, their searchable text, model identity and current source revision. Foreign keys bind each row to exactly one memory, chat message, captured Gmail message or managed message. Search joins back to the live source and checks its revision and access predicates before ranking. Source changes affecting indexed content, identity or eligibility physically purge old chunks in the same transaction. Mail read and other metadata-only updates preserve the cache. Deletes cascade, including memory resets and deleted conversations. After inference, the writer locks the source and compares its current revision before storing any chunk. A late response cannot recreate a deleted source or attach old text to an edited one. Legacy memory vectors without model identity remain inactive.

Preparation normalizes Unicode whitespace before hashing and chunking the whole canonical search text into 2,000-character pieces. It advances in bounded batches. Indexed-source counts include a source only after all of its current chunks exist. Partial vectors can contribute results while the UI reports incomplete coverage. Capture and HTML text-normalization bounds apply to the represented source itself, independently of chunk coverage.

Mail search uses canonical decoded subjects and readable HTML fallback text from versioned capture metadata. Raw headers and bodies stay unchanged. Bounded preparation repairs legacy metadata with source comparisons that fence concurrent capture, edits and deletion. Unrepaired messages remain pending in coverage. Search displays the original Gmail message timestamp or managed-mail sent timestamp, rather than the time of capture or metadata repair.

A semantic request registers an actor, billing mailbox and source kind in `semanticIndexRequest`. The maintenance Worker continues incomplete preparation and checks completed registrations for newly changed sources. Leases, revision checks and token-fenced checkpoints protect concurrent work and retries. The queue retains source identifiers and progress, never search queries. Billing always uses the requesting actor and mailbox, rather than selecting an arbitrary organization for user-wide memories. Automatic learning can remain paused; indexing does not change learned facts. **Stop background preparation** removes that scoped registration. A current batch may finish. A later submitted search resumes retained-content preparation.

The search lease serializes source-chunk preparation. A query can still embed its own text and retrieve current vectors while another operation prepares sources. It does not duplicate that operation's pending chunk work or change its lease. Query usage follows the same billing and failure rules; provider failures still fail the request.

Gmail semantic search initially covers messages already retained by Quieter. Normal Gmail search continues to cover the provider mailbox. **Prepare older mail** explicitly requests a resumable historical scan and explains that preparing search uses AI balance. The scan performs authorized Gmail reads and canonical snapshot writes, without changing Gmail state. Search imports do not queue importance analysis or memory learning. Provider page and remaining-message checkpoints let retries continue; completed scans are not restarted by repeated preparation requests. Stopping background preparation removes the registration, so restarting an older-mail scan requires another explicit request.

## Local operation and rollout

Use `vp run dev:full` for the web and local Worker runtimes. Automatic bulk learning and scheduled search indexing remain disabled locally. Submitted semantic searches can still prepare their bounded batch. Run `vp run dev:trigger memory <local-user-id>` for that user's queued bootstrap and learning work. Run `vp run dev:trigger semantic-index <local-user-id> <mailbox-id> <memory|chat|mail>` for bounded search preparation in one authorized scope. The mail trigger also advances an older-mail import already requested in the UI. Use separate budget-limited development AI credentials through SST Secrets or the approved ignored local configuration. Existing Gmail watch-ownership and provider-write rules still apply.

Apply schema changes before deploying the new readers and workers. The search migrations create source-bound embedding storage, preparation leases, durable requests and import checkpoints. The native-search migration enables `tin`, adds its text index and installs source invalidation triggers. A corrective migration narrows mail invalidation to relevant source changes. The native-search, import-column and invalidation-correction migrations carry `-- quieter:contract` under the existing migration policy because extension creation, triggers and required columns are outside its ordinary additive allowlist. Review these statements before the protected production migration workflow. The policy itself is unchanged.

The BGE-M3 switch needs no additional schema migration or credential. Existing OpenAI vectors keep their original model key and do not count toward BGE coverage. The existing bounded indexer prepares missing BGE chunks from retained source text. No fact extraction or mail refetch is needed for this rebuild. Source invalidation still removes obsolete chunks across every model.

During an authorized rollout, drain the previous maintenance consumer before enabling the BGE consumer. Old and new deployments cannot mix vector spaces, but old workers can still spend on OpenAI and delay new preparation. Inspect active deployments and model coverage through the protected workflow before rollout. Live logical-database inventory was unavailable through the MCP role during this switch, so no empty-index assumption is warranted.

An environment with an older prepared index has partial BGE semantic coverage until rebuilding completes. Retained-text history matching and deterministic memory selection remain available when the normal request succeeds. Provider and billing failures still fail semantic search. This release does not provide a dual-model cutover. Preparation status reads current authorized BGE coverage without AI calls and also requires any explicitly requested historical import to finish. Saved queue counters cannot establish readiness for another model. Displayed result lists refresh only on explicit submission, so their incomplete-results warning follows the search snapshot.

Historical memory vector columns, mailbox ownership columns and retired job tables remain inactive for a later contract release. The new model/version identity excludes unknown legacy vectors. No production migration, extension activation, data cleanup or deployment was performed for this verification. See the [semantic-search evidence](reviews/semantic-search/README.md).
