# Roll out independent domain challenges

This change separates pending DNS challenges from verified ownership. Teams can prepare independent challenges for the same domain. Only one team can verify it. Established ownership survives DNS failures and mode changes until that team removes the domain.

This PR is the expand release. Its committed migrations retain `mail_domain_domain_unique`, so the ordinary main-push deployment can apply every migration before replacing Workers. Competing pending challenges remain unavailable during expansion. This release does not yet resolve the pending-reservation onboarding denial.

1. Deploy the expand release through the protected normal deployment workflow. It adds and backfills permanent ownership, installs a trigger that preserves ownership proved by old handlers during the overlap, and adds organization-scoped challenge uniqueness and exclusive verified ownership. Keep the global domain uniqueness constraint.
2. Observe the web release manifest and wait until every pre-expand release has expired. The router retains the previous web release for 12 hours from release planning. Also wait for already admitted old domain-management requests to finish. Confirm every process serving domain setup, checks, mode changes, removal, and Domain Connect callbacks uses the new locking code. A successful deploy alone does not satisfy this gate.
3. After recording that drain evidence, prepare a separately reviewed contract PR. Remove only `unique("mail_domain_domain_unique").on(table.domain)` from `packages/database/src/schema.ts`, run `vp run db:generate`, and prepend `-- quieter:contract` to the generated migration SQL. Confirm its only SQL statement is `ALTER TABLE "mailDomain" DROP CONSTRAINT "mail_domain_domain_unique";`. Keep both new uniqueness constraints and the ownership trigger. Run `vp run db:check` and run `vp run db:test-migrations` against a disposable loopback `quieter_migration_test` database. Run `vp test packages/orpc/tests/mail-domain-claims.integration.test.ts --maxWorkers=1 -t 'after the separately reviewed contraction'` against that migrated database before publishing the contract PR. The expand-only compatibility test requires the old global constraint and is excluded from this contracted-schema run.
4. Merge and deploy the contract PR only after protected review confirms the drain evidence. The normal all-migrations deployment now removes global uniqueness, enabling competing pending challenges. Do not package this migration in the expand PR or deploy it while any pre-expand handler can run.
5. Verify two test teams can prepare independent challenges on a dedicated test domain. Publish only the rightful team's TXT challenge and complete verification. Confirm another team's challenge cannot verify or remove the owner's provider resources.

The migration runner has no release-stage cutoff. The SQL review marker `quieter:contract` does not enforce release order or drain old Workers. This PR enforces the expand boundary by excluding the contraction migration and retaining global uniqueness in both the schema and latest generated snapshot. The contract PR and its drain evidence are required release gates.

The domain-claim integration suite explicitly removes global uniqueness on its disposable database to exercise the future contracted behavior, then restores it after cleanup. This test-only transition is not part of the deployment migration path.

The backfill preserves current verified rows, rows with a verification timestamp, and domains already used by managed mailboxes. Historical ownership without any retained proof cannot be reconstructed from a failed row alone. Review such domains before contraction if prior verification was cleared before the expand migration.

Pending challenges retain their organization-specific token across retries. Removing a challenge invalidates its identifier and deletes its Domain Connect attempts through the existing foreign key. Recreating it generates a new token. Pending challenges do not reserve ownership, so no expiry job is required.

Provider identities remain shared while any challenge exists. Removing a losing pending claim leaves shared resources intact. Removing the established owner disables incoming routing; removing the final claim deletes both the identity and routing resources. These operations and verification run under the same transaction-scoped domain lock.
