# Coding Guidelines

`AGENTS.md` is policy, not reference documentation. Follow these rules at all times; use `docs/` for explanations and runbooks. When you are an agent, do not edit this file unless you are asked to do so by the user.

## Boundaries

- Do not make `packages/*` depend on `apps/*`.
- Do not access the database from `apps/*` or UI code. Use `@quieter/orpc`.
- Put shared components in `packages/ui`; app code consumes `@quieter/ui`.
- Do not import Base UI or Vaul directly from app code.
- Keep provider details behind package boundaries. Use provider-neutral mail contracts in UI and application-facing code.
- Keep Gmail REST calls, credential decryption, and token refresh server-side.
- Read environment variables through `@quieter/env`; do not add ad hoc env parsing or direct custom-variable reads outside required bootstraps.
- Give every Worker request its own database client through `withRequestDatabaseClient`; never share I/O-bound clients across requests.
- Keep AWS and Cloudflare handler dependency graphs deployment-safe. Run the relevant boundary and bundle checks when changing handler imports.
- Do not hand-edit generated route trees or migration snapshots unless absolutely necessary.

## Security and isolation

- Keep Google identity OAuth separate from Gmail OAuth and PKCE. Identity tokens must never grant or read Gmail.
- Encrypt credentials at rest and keep them owned by one user.
- Keep Gmail mailboxes private to their owner. Require explicit grants for managed mailbox access.
- Include `mailboxId` in every mailbox-scoped query key, cache write, chat, compose session, and mutation.
- Keep consent browser-only. Load analytics only after measurement consent.
- Never send message content, search text, mailbox/user identifiers, email addresses, or private URL parameters to analytics; you can log numbers but not personally identifiable information.
- Report unexpected failures to Sentry; filter expected user and authorization states.
- Load AI context through `loadAiAgentContext`; never query `aiMemory` directly.
- Do not expose infrastructure, provider, or model names in user-facing copy unless the user must configure or interoperate with that name. User-friendly names, not technical terms and names.

## Database and operations

- For schema changes: edit `packages/database/src/schema.ts`, run `vp run db:generate`, review the migration, and run `vp run db:check`.
- Use expand/contract for changes that can break a running release and note that to the user. Use the PlanetScale MCP to review queries and other database activity from production and development databases.
- Use `db:push` only against disposable local databases.
- Never apply production migrations locally, rewrite migration history, or put production credentials in `.env.local`.
- Use only loopback PostgreSQL or the allowlisted `quieter_dev` database locally.
- Run `vp run env:doctor` after local environment changes.
- Production database writes, role/credential changes, backups, and deploys require explicit authorization and protected workflows; see the PlanetScale MCP and LLM docs for more details.

## Code style

- Keep types strict. Avoid `any`, unnecessary casts, effects, abstractions used once, placeholders, dead fallbacks, and obsolete compatibility branches.
- Do not create trivial single-line or single-statement helper functions (e.g. `isRecord`, `parseJson`); inline the expression directly at each call site, even if that means slight duplication in multiple places.
- Keep comments minimal — only for hacky or high-complexity code where intent isn't obvious from the code itself.
- Use TanStack Query for server state and TanStack Store for complex client-only workflows.
- Use named theme colors. Do not use arbitrary Tailwind colors.
- Do not use native `<select>` or direct Base UI/Vaul imports in app code. Use only native interactive elements if absolutely necessary, otherwise use the `@quieter/ui` package or extend shared components.
- Use object syntax for conditional classes in `cn(...)`.
- Give icon-only controls a shared tooltip and concise `aria-label`.
- Preserve existing layout, density, and hierarchy during incremental UI work.
- Do not use the middle-dot character or any HTML/entity/escape spelling; prefer styled div elements as separators or just commas.
- The lint rules in this codebase are very strict. Try to adhere to them, but if working around a warning or error would be too complicated or overly complex for the situation, it is acceptable to disable the lint rule for that specific line or function with an inline suppression comment.

## Finish

- Add focused tests for deep and complex behavior changes.
- Update documentation only when architecture, tooling, or operations change.
- Before finishing any complex changes, run the following checks (not needed for very small and safe changes or when only changing documentation):

  ```bash
  vp check --fix
  vp test
  vp run -r build (optional)
  ```

- Use Conventional Commits when committing. Commit unrelated work too unless it seems to be currently changing, incomplete, or the user specified otherwise.

# Important

- Any of these guidelines may be overridden by the user, but the user must be aware of the consequences and understand the trade-offs.
- Whilst implementing any code changes, think of security implications, best practices in the industry, and other related code changes that may be required. Keep your changes relatively scoped to the user's request but always consider the bigger picture and long-term implications, and notify the user in the handoff of any skipped steps, areas of concern, or any other relevant information.
- Regularly commit your work and when you are completely done with a feature or change, push it to remote. When on main, first create a feature branch and then push it to remote.
- Extremely destructive actions or changes have to be specifically approved by the user. In this case, stop your current turn temporarily and ask the user for approval.
